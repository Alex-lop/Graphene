# Best-of-N for Graphene: several attempts at one leaf, keep the best

Research brief, 20 Oct 2026. Graphene today (`run.py`): one worktree per leaf (`.graphene/worktrees/<id>`, branch `graphene/<id>`), up to 3 attempts one after another, the second Claude Code attempt `--resume`ing the first session with the refusal, each capped at `--max-budget-usd 2`, the check run in a clean copy, then a `--no-ff` merge.

## 1. Products: how N candidates are shown, who picks

- **OpenAI Codex.** Cloud "Best of N" shipped 2025-06-13: "Codex can now generate multiple responses simultaneously for a single task" ([changelog](https://developers.openai.com/codex/changelog)). The CLI has `codex cloud exec --attempts 1-4`, "Number of assistant attempts (best-of-N) Codex cloud should run" ([CLI reference](https://developers.openai.com/codex/cli/reference)). A third-party post says Codex "does not currently score or rank attempts for you — selection is manual", each attempt billed ([post](https://codex.danielvaughan.com/2026/04/01/codex-cloud-exec-best-of-n-attempts/)); unverified against OpenAI's docs.
- **Cursor.** `/best-of-n sonnet, gpt, composer fix the flaky logout test` "runs the same task across multiple models at once, each in its own worktree"; "a parent agent provides commentary on the different results so you can pick the best one, or ask it to merge parts" ([Cursor 3, Apr 2026](https://forum.cursor.com/t/cursor-3-worktrees-best-of-n/156507)). Cursor 2.2 added a judge: "After all parallel agents finish, Cursor evaluates each solution and picks a winner... The selected agent gets a comment explaining why" ([Dec 2025](https://forum.cursor.com/t/cursor-2-2-multi-agent-judging/145826)).
- **Claude Code.** `claude --worktree <name>` puts a session in `.claude/worktrees/<name>` on branch `worktree-<name>`; comparing is by hand ([docs](https://code.claude.com/docs/en/worktrees)). Agent teams (experimental) suggest "competing hypotheses" for debugging; nothing picks among patches ([docs](https://code.claude.com/docs/en/agent-teams)). Anthropic's own best-of-N: "We sample multiple parallel attempts. We discard patches that break the visible regression tests in the repository... We then use an internal scoring model to select the best candidate": 77.2% → 82.0% for Sonnet 4.5 ([announcement](https://www.anthropic.com/news/claude-sonnet-4-5)); 72.5 → 79.4 (Opus 4), 72.7 → 80.2 (Sonnet 4) ([Claude 4](https://www.anthropic.com/news/claude-4)). N is never stated.
- **GitHub Copilot coding agent.** "Copilot can only work on one branch at a time and can open one pull request per task" ([docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). Agent HQ's mission control: "choose from a fleet of agents, assign them work in parallel" ([GitHub blog](https://github.blog/news-insights/company-news/welcome-home-agents/)); press says one task can go to several agents for comparison ([SiliconANGLE](https://siliconangle.com/2025/10/28/github-tackles-vibe-coding-chaos-control-center-ai-coding-agents/)), unverified in GitHub's docs.
- **Jules, Devin.** Jules: one plan you approve, a VM per task, 3/15/60 concurrent tasks by plan ([docs](https://jules.google/docs), [limits](https://jules.google/docs/usage-limits)). Devin: managed Devins split work across VMs behind an "Auto-approve child sessions" toggle ([docs](https://docs.devin.ai/product-guides/advanced-mode), [blog](https://cognition.com/blog/devin-can-now-manage-devins)). - **Crystal/Nimbalyst, Conductor, Sculptor, uzi, Vibe Kanban.** All run N sessions in worktrees or containers and leave the pick to the person's eyes. Crystal: "Test, compare approaches", deprecated Feb 2026 for [Nimbalyst](https://github.com/Nimbalyst/nimbalyst) ([repo](https://github.com/stravu/crystal)). Vibe Kanban is sunsetting ([repo](https://github.com/BloopAI/vibe-kanban)).

Pattern: every shipped tool hands N diffs to a person, or (Cursor) asks an LLM afterwards; none uses the project's own tests as the selector. Graphene has a deterministic check per leaf, so it can.

## 2. Research: what selection works

**Coverage is cheap; selection is the bottleneck.** Repeated sampling lifts the share of problems with at least one correct sample "from 15.9% with one sample to 56% with 250 samples" (SWE-bench Lite), but without a verifier "majority voting and reward models plateau" ([Large Language Monkeys](https://arxiv.org/abs/2407.21787)). CodeMonkeys: 10 trajectories per issue reach 69.8% coverage; a random pick scores 45.8%, its selector 57.4%, "approximately half of the gap"; about $2,300 for 500 issues ([paper](https://arxiv.org/html/2501.14723v2)). "This pass@k-to-pass@1 gap is a post-generation problem" ([PatchFusion, 2026](https://arxiv.org/abs/2607.01597)).

**Tests first, then agreement.** Agentless samples 40 patches, keeps those with the fewest regression failures, then those passing a reproduction test, normalises the AST and majority-votes: 32.0% on Lite at $0.70 an issue ([paper](https://arxiv.org/html/2407.01489v2)). Trae Agent (N=3; Claude 3.7, Gemini 2.5 Pro, GPT-4.1): dedupe, regression filter (33.04% false positives, 3.69% false negatives), then an LLM selector with tools voting N times; random pick 61.33% → 66.40% with Claude; ties "broken randomly" ([paper](https://arxiv.org/html/2507.23370v1)). ByteDance: "LLM-as-a-Selector peaks when the sampling space is 5 or 6" ([blog](https://se-research.bytedance.com/blogs/trae-on-swe-bench-verified-71)). Voting breaks on ties: "multiple patches achieve the same test passing rate; in such cases, majority voting favors patches with higher occurrences" ([TestPrune](https://arxiv.org/html/2510.18270v1)). Execution-based verifiers "suffer from low distinguishability", execution-free ones "are biased and often rely on stylistic features"; each saturates at 42–43%, combined 51% ([R2E-Gym](https://arxiv.org/abs/2504.07164)).

**Candidates' own tests as referee.** CodeT runs every sample against every generated test and keeps the largest agreeing group, "dual execution agreement" ([paper](https://arxiv.org/abs/2207.10397)); AlphaCode "filter[s], cluster[s], and rerank[s]" down to 10 submissions ([DeepMind](https://deepmind.google/blog/competitive-programming-with-alphacode/)); S* "generates distinguishing test inputs for pairwise comparisons between candidate programs" ([paper](https://arxiv.org/abs/2502.14382)); CodeMonkeys votes with model-written tests, keeps the top 3, then one selection trajectory.

**Learned critics and early stopping.** OpenHands: 60.6% for one rollout → 66.4% with five and a trained critic ([2025](https://openhands.dev/blog/sota-on-swe-bench-verified-with-inference-time-scaling-and-critic-model)); in 2026, on instances where runs disagree, Best@8 73.8% vs Random@8 57.9%, and stopping once the critic is satisfied averaged 1.35 attempts for most of the gain ([2026](https://openhands.dev/blog/20260305-learning-to-verify-ai-generated-code)). SWE-Gym's verifier: 20.6% → 32.0% at Best@16, oracle 42.8% ([paper](https://arxiv.org/html/2412.21139v1)).

**Diversity.** Other models add coverage beyond one model's samples: Trae's oracle at N=3 is 70.0% for Claude alone, 73.4% mixed ([paper](https://arxiv.org/html/2507.23370v1)); selecting across five different SWE-bench systems: coverage 80.8%, best member 62.8%, selected 66.2% ([CodeMonkeys](https://arxiv.org/html/2501.14723v2)); a committee of agents: best single 27.3% → 55% ([DEI](https://arxiv.org/abs/2408.07060)). The pick stays hard: Trae's mixed pool selected 65.67%, under Claude-only 66.40%.

**Pitfalls.** Reward hacking "emerges spontaneously in frontier models"; generated exploits scored "near-perfect... without solving a single task" on most of 10 benchmarks ([BenchJack](https://arxiv.org/abs/2605.12673)): a candidate that edits the check's tests must not win. Anthropic stresses "no hidden test information is used". Review fatigue is the Cursor users' complaint: "using parallel agents multiplies the amount of reviewing I have to do" ([forum](https://forum.cursor.com/t/what-s-the-point-of-multiple-agents/141805)); Claude Code's docs say team cost "scale[s] linearly" ([teams](https://code.claude.com/docs/en/agent-teams)).

## 3. Answers

- *With a deterministic check:* it is the filter, as in every lab recipe above; among passers use execution evidence first (the rest of the suite; each candidate's new tests run on the others), then size, then cost; never random.
- *Race or tournament:* a race (first to pass lands, the rest stop) is cheapest, and early stopping shows it keeps most of the gain; a tournament is what makes tie-breaks and comparison possible.
- *Diversity:* a fresh session beats resuming the one that failed (anchoring); a second executor adds about 3 points of coverage at N=3 but needs a better picker. A judge model is weak alone (stylistic bias, peaks at 5–6 candidates); fine as commentary.

## Recommendations for Graphene

1. **`graphene run --candidates N`** (default 1). N ≥ 2 starts N executors on one leaf at once, in `.graphene/worktrees/<id>.a`, `.b`... on branches `graphene/<id>/a`..., sharing the leaf's scope (overlapping leaves wait, as now). The cockpit's "⏎ try again" on a leaf that came back defaults to 2: `a` resumes the failed session with the refusal (today's path), `b` is a fresh session told the refusal; three serial attempts become at most 2×2, the same worst case.
2. **Candidates differ by executor when `--with` is given more than once** (`--with claude... --with codex...`, round-robin), else by session (resumed vs fresh); neither `claude -p` nor `codex exec` exposes temperature.
3. **Selection = the check, then four tie-breaks in order, all recorded:** (i) the project's full test command, if set in settings, in each passer's clean copy: fewest failures; (ii) cross-tests: each passer's added or changed test files run in the other passers' trees; most of the others' tests passed wins (CodeT/CodeMonkeys), and a candidate that deleted or edited a test the check runs (`check_paths`) loses outright; (iii) fewer changed non-test lines; (iv) fewer dollars, then the earlier finish. Deterministic, never random. `--judge` (off) has the planner model write a one-paragraph comparison into the record; it never picks.
4. **Tournament by default, race with `--first`.** N is small (2–3) and the point is seeing which was best; `--first` stops the others when one passes, for cheap leaves.
5. **Cockpit:** one row per leaf, as now, reading "2 candidates · b picked: passes a's tests, 31 lines vs 58"; `c` cycles the pick (diff, check output and cost follow), `i` shows the matrix, Enter lands the shown candidate. Losers' branches stay until the leaf lands, then go.
6. **Record:** a `candidate` row per candidate (letter, executor, session, worktree); the existing `attempt`, `ended`, `check_passed`, `check_failed` rows keyed by letter; one `tie_break` row (suite failures, cross-test matrix, diff stat, dollars, seconds); `picked` (rule, `by: graphene|person`); `landed` with the letter.
7. **Cost:** worst case N × `--max-budget-usd` ($4 at N=2, $6 at N=3), held on the night's ledger before start, as today; `--max-usd` still caps the run. Tie-breaks cost test time, not tokens. Expected gain, from the literature, not Graphene: +5 points at N=3 (Trae), +5.8 at N=5 (OpenHands); measure it on the demo plan before the README claims it.
