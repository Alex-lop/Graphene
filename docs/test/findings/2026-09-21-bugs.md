# Product bugs the second collaboration test found

Written while the runs were going. Nothing here is fixed: `src/` was not mine to touch this run.
Each one is a command, an output, and where it bit.

## 1. A redirect to a whitespace-only target is treated as a write, and blocked

`attribute.bash_written_paths` drops `/dev/null`, `-`, the empty string and anything starting `-`,
but not a path that is only whitespace. A quoted newline reaches the gate as a file, and the gate
blocks the command because no node's scope covers it.

```sh
python3 - <<'PY'
import sys; sys.path.insert(0, "src")
from pathlib import Path
from graphene_debrief.attribute import bash_written_paths
print(bash_written_paths('echo hi > "\n"', Path("/tmp/x")))
PY
[('\n', 'write')]
```

Every one of these does it too: `cat > "\n" <<EOF`, `tee '\n'`, `touch '\n'`, `cp a '\n'`,
`echo x >> "\n"`, `sed -i '' -e 's/a/b/' '\n'`.

Where it bit: `feeds-tuesday-graphene-1`, at 2026-09-21T06:46:32.615Z, an executor under
`graphene run` had a command blocked, and the store holds

    node_log: wire-xml | denied | run:claude | {"path": "\n", "how": "shell"}

That is the only `refused_writes` in the whole test, and it is not a boundary catching a wander —
it is a parse artefact. A blocked `PreToolUse` is never written to `tool_events`, so the command
itself is not recoverable from the store; only the repro above shows the shape of it.

Smallest fix: `src/graphene_debrief/attribute.py`, the guard at the top of the loop in
`bash_written_paths`, add `not path.strip()` beside the `/dev/null` case.

## 2. Executor cost through `graphene run` is written down and never read

`run.run_node` writes `done.stdout + done.stderr` to `.graphene/runs/<node>-<attempt>.txt` and
parses none of it, and the default `--with` carries no `--output-format json`. So a person running
`graphene run` cannot see what a run cost — not in the plan, not in `graphene plan log`, nowhere.

It is recoverable if, and only if, the person puts `--output-format json` into `--with`
themselves: that file is then the vendor's own JSON object, and `tally.py` reads `total_cost_usd`,
`num_turns` and `session_id` out of it. That is what this harness now does.

What it is worth: in `feeds-dense-graphene-1`, $0.97 of the run's $1.55 was in those files. A
report counting only what the person's own shell saw would have printed $0.58 — 2.7 times under,
which is the direction the 20 September report already suspected and could not measure.

Smallest fix: `json.loads(done.stdout)` when `Path(argv[0]).name == "claude"`, and put
`total_cost_usd`, `num_turns` and `session_id` into the `finished` entry's detail dict in
`run.run_node`, beside the `changed:` that is already there.

## 3. `graphene plan propose -` exists, and agents write a file in the repo anyway

`propose` takes `-` and reads stdin. In `feeds-dense-graphene-1` the person's message said so in
those words, and the executor wrote `.northwind-plan.json` into the repository regardless, 56
lines, then removed it. The old tally would have counted that twice over — once as a `Write`
event, once as the removal in a `Bash` change list. 52 of that run's 301 naive churn lines are
that one file counted twice.

Not a defect in `propose`; a defect in what an agent is told. Nothing in the tool's own help or
output pushes an agent towards `-`, and the doc string reads *"A JSON file ('-' for stdin)"* — the
file comes first, and the file is the one the agent picks.

## 4. A sibling leaf landing mid-flight is charged to the leaf still flying

The worst one, and the only one that cost a person real time. `graphene run --parallel 2`, in
`feeds-dense-graphene-2`. The plan log, with the times as the store holds them:

    07:08:01.850  xml-wiring      started    run:claude   base 46c9072, worktree .../worktrees/xml-wiring
    07:08:03.087  readme-sources  landed     graphene run commit 7444799, branch graphene/readme-sources
    07:08:21.821  xml-wiring      refused    claude:2ef348f0  {"outside": ["README.md (in the worktree …/repo)"]}
    07:08:35.267  xml-wiring      refused    claude:2ef348f0  {"outside": ["README.md (in the worktree …/repo)"]}
    07:08:45.835  xml-wiring      refused    claude:2ef348f0  {"outside": ["README.md", "README.md (in the worktree …/repo)"]}
    07:08:50.945  xml-wiring      refused    claude:2ef348f0  {"outside": ["README.md (in the worktree …/repo)"]}
    07:08:58.343  xml-wiring      released   claude:2ef348f0

`readme-sources` landed its README.md change into the main checkout 1.2 seconds after `xml-wiring`
started in its own worktree. From then on `graphene node done xml-wiring` compared the main
checkout against the boundary it had marked, saw README.md different, and charged it to the only
node holding anything. `xml-wiring`'s scope is `config/defaults.py`, `normalize/fields.py`,
`cli/main.py`; it never touched README.md, and its own worktree had README.md unmodified. Its
executor said exactly that and gave the node back:

> The three scoped edits are done and tests.test_contract/test_csvfeed pass, but done refuses:
> README.md is flagged as changed outside scope. I did not touch it; my worktree has it
> unmodified. The flag comes from commit fef56ef on main ('List xml in the README's supported
> sources'), made outs…

The person then did the node by hand in the outer checkout: `started` 07:09:47, `finished`
07:14:33. **Four and a half minutes of a person's attention, spent on a race between two leaves of
their own plan.** On a night run nobody is watching, that leaf waits until morning.

The boundary is marked per checkout (`plan_meta`, `boundary:<path>`), and landing re-marks it on
the target — but a leaf already in flight was told a boundary that the landing invalidated. Either
a flying leaf's boundary has to be re-marked when a sibling lands, or `done` has to ask which
commit changed a file before charging it to anyone.

## 5. Work done by hand in the checkout is invisible to the next parallel worktree

Straight after, same run:

    07:16:04.725  xml-tests  started   run:claude  base 7444799, worktree .../worktrees/xml-tests
    07:16:59.978  xml-tests  released  claude:80e55585

> tests/test_xmlfeed.py is written (7 tests) and passes when xml-wiring's config/defaults.py,
> normalize/fields.py and cli/main.py changes are applied in-process, but those edits were never
> committed or merged. They sit uncommitted in the main checkout, and this branch has
> ENABLED_SOURCES=('cs…

`--parallel 1` "works in this checkout and commits nothing" — that is what its help says — and
`--parallel N` cuts each worktree from `HEAD`. Mix the two in one plan, which is exactly what
happens the moment a person does one leaf themselves, and the parallel worktree is cut from a
commit that does not contain the person's work. The person's fix was to rerun the leaf with
`--parallel 1 --node xml-tests`, which is not a thing the tool tells you.

## 6. A node's check runs under `/bin/sh`, and nothing says so

Same run, the last leaf:

    07:22:36.864  infer-source  check_failed  claude:a350d5d6
      {"command": "diff <(python3 -m cli.main load samples/prices.xml) <(python3 -m cli.main load …"}

The check is a perfectly ordinary bash line using process substitution. `graphene` runs checks
under `/bin/sh`, where `<(...)` is a syntax error, so the check failed on its own syntax and not on
the code — which was correct, and the person verified it by hand in bash. They finished the node
with `graphene node done --override`, and the store now carries an `overruled` entry for a node
whose code was right all along.

`graphene node add --check` says "The command that must pass for it to be done". It does not say
which shell runs it. A person writing a check in the shell they are standing in will write bash.
