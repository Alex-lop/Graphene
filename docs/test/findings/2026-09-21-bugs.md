# Product bugs the second collaboration test found

Written while the runs were going. Nothing here is fixed: `src/` was not mine to touch this run.
Each one is a command, an output, and where it bit.

## 1. A redirect to a whitespace-only target is treated as a write, and blocked

`attribute.bash_written_paths` drops `/dev/null`, `-`, the empty string and anything starting `-`,
but not a path that is only whitespace. A quoted newline reaches the gate as a file, and the gate
blocks the command because no node's scope covers it.

```sh
python3 - <<'PY'
import sys; sys.path.insert(0, "src")
from pathlib import Path
from graphene_debrief.attribute import bash_written_paths
print(bash_written_paths('echo hi > "\n"', Path("/tmp/x")))
PY
[('\n', 'write')]
```

Every one of these does it too: `cat > "\n" <<EOF`, `tee '\n'`, `touch '\n'`, `cp a '\n'`,
`echo x >> "\n"`, `sed -i '' -e 's/a/b/' '\n'`.

Where it bit: `feeds-tuesday-graphene-1`, at 2026-09-21T06:46:32.615Z, an executor under
`graphene run` had a command blocked, and the store holds

    node_log: wire-xml | denied | run:claude | {"path": "\n", "how": "shell"}

That is the only `refused_writes` in the whole test, and it is not a boundary catching a wander —
it is a parse artefact. A blocked `PreToolUse` is never written to `tool_events`, so the command
itself is not recoverable from the store; only the repro above shows the shape of it.

Smallest fix: `src/graphene_debrief/attribute.py`, the guard at the top of the loop in
`bash_written_paths`, add `not path.strip()` beside the `/dev/null` case.

## 2. Executor cost through `graphene run` is written down and never read

`run.run_node` writes `done.stdout + done.stderr` to `.graphene/runs/<node>-<attempt>.txt` and
parses none of it, and the default `--with` carries no `--output-format json`. So a person running
`graphene run` cannot see what a run cost — not in the plan, not in `graphene plan log`, nowhere.

It is recoverable if, and only if, the person puts `--output-format json` into `--with`
themselves: that file is then the vendor's own JSON object, and `tally.py` reads `total_cost_usd`,
`num_turns` and `session_id` out of it. That is what this harness now does.

What it is worth: in `feeds-dense-graphene-1`, $0.97 of the run's $1.55 was in those files. A
report counting only what the person's own shell saw would have printed $0.58 — 2.7 times under,
which is the direction the 20 September report already suspected and could not measure.

Smallest fix: `json.loads(done.stdout)` when `Path(argv[0]).name == "claude"`, and put
`total_cost_usd`, `num_turns` and `session_id` into the `finished` entry's detail dict in
`run.run_node`, beside the `changed:` that is already there.

## 3. `graphene plan propose -` exists, and agents write a file in the repo anyway

`propose` takes `-` and reads stdin. In `feeds-dense-graphene-1` the person's message said so in
those words, and the executor wrote `.northwind-plan.json` into the repository regardless, 56
lines, then removed it. The old tally would have counted that twice over — once as a `Write`
event, once as the removal in a `Bash` change list. 52 of that run's 301 naive churn lines are
that one file counted twice.

Not a defect in `propose`; a defect in what an agent is told. Nothing in the tool's own help or
output pushes an agent towards `-`, and the doc string reads *"A JSON file ('-' for stdin)"* — the
file comes first, and the file is the one the agent picks.
